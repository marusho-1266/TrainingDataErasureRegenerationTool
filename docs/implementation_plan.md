# 実装計画：学習用書き込み消去ツール（Flutter）

本書は [`spec.md`](./spec.md) を前提に、実装フェーズ全体の順序・成果物・ゲート・並行タスクを定義する。**仕様とのトレース**はセクション末尾の対応表を参照する。

## 1. ゴールと前提

- **プロダクトゴール**: オンデバイスでスキャン → マスク → inpainting → ローカル保存 → PDF と共有までの MVP（受け入れは `spec.md` §2）。
- **技術ゴール**: `google_mlkit_document_scanner` + `onnxruntime_flutter` + （必要に応じ）`image` / `opencv_dart` + PDF パッケージの組み合わせが、対象端末で **§3 PoC ゲート**を満たすこと。
- **リポジトリ現状**: Flutter プロジェクトは未作成。最初のマージでは **Flutter 新規作成 + 最小実行**まで含める。
- **非目標（MVP 外でも可）**: 手動四隅補正、Redo、多言語、アプリストア公開までのマーケ準備だけを先に完璧にすること。

## 2. 並行して進める項目（§15 のクリティカルパス）

イテレーション開始時に **§15 のどれをクローズするか**をチケットに書く（`spec.md` §15.1）。PoC 着手前または PoC と並行で、次を優先して合意する。

| 優先 | 項目 | 成果物 |
|------|------|--------|
| P0 | 最小端末・最小 OS（仮でも可、その後確定値で spec 更新） | 対応表（機種・OS・メモリ目安） |
| P0 | inpainting ONNX 候補 1〜2 と §4.1 の一次記入 | 埋まった確認表または却下理由 |
| P0 | 代表サンプル画像セットの準備開始 | N 枚・権利処理の運用決定 |
| P0 | モデル配信方針 | 同梱 vs 初回 HTTPS（CDN の場合 §11.3 のユーザー向け文言案） |
| P1 | 計測・クラッシュ SDK 採否 | 無なら開発中もネットワーク依存をモデル DL のみに限定する方針 |
| P1 | PDF 余白・JPEG 初期固定値 | 実装時定数、`spec.md` §10 と整合 |

## 3. フェーズ構成（概要）

```
Phase A（Week 規模は目安）: PoC / Step 0  … ONNX + 前後処理 + 実機計測 → §3 GO/NO-GO
Phase B: Step 1–2         … Flutter アプリ壳 + Document Scanner + プレビュー + ローカル保存
Phase C: Step 3–4         … 推論パイプライン本番化 + マスク UI + 消去強度
Phase D: Step 5–6         … PDF + 共有 + ライブラリ一覧・複数選択
Phase E: リリースハードニング … §2 受け入れテスト、§7 エッジ、§14 法務（ストア直前）
```

以下、各フェーズの**主タスク**・**完了条件**・**リスク**を記載する。

## 4. Phase A — Step 0（PoC）

### 4.1 目的

本番 UI を作る前に、**選定モデル**が iOS/Android の候補端末で **§3.1**（時間・安定性・メモリ・Execution Provider）を満たすかを検証する。

### 4.2 タスク

1. **Flutter プロジェクト作成**（最小 `pubspec`、iOS/Android ビルド確認）。
2. **`onnxruntime_flutter` スパイク**: 固定入力（ダミー画像 or 固定バッファ）でセッション作成 → 1 回推論。CPU のみでも可を最初の基準とし、可能なら EP（CoreML / NNAPI 等）を試す。
3. **前処理スパイク**: 長辺リサイズ（1024 仮）、正規化、マスクテンソル結合を Dart + `image` で実装（重い場合のみ `opencv_dart` を検討）。
4. **計測**: ウォールタイム、ピークメモリ（Xcode Instruments / Android Profiler）、クラッシュ可否を記録。
5. **§4.1 更新**: 採用 or 辞退の判断と入力形状・量子化前提を文書化。

### 4.3 完了条件（ゲート）

- §3 の表を**実数で**1 行でも埋められる状態（または未達として「長辺 768」「別モデル」を仕様変更として記録）。
- 「アプリ構造をモデル形状にロックしてよい」と PO が承認。

### 4.4 リスク・回避

| リスク | 回避 |
|--------|------|
| 30 秒超 / OOM | 解像度引き下げ・軽量モデル・タイル分割（コスト許容時） (`spec.md` §3.2) |
| iOS/Android で EP が異なる | 両 OS で「公式にサポートされる EP + CPU フォールバック」を明示 |

## 5. Phase B — Step 1〜2（スキャンと保存）

### 5.1 Step 1: ドキュメントスキャンと Shell

- **`google_mlkit_document_scanner` 統合**（`spec.md` §16 チェックリストをタスク分解）。
- 権限（カメラ、`READ_MEDIA` / Photos 相当等）・**§7** の検出失敗時メッセージ。
- **ホーム画面**の最低限（「新しいページを撮影」相当の導線）。

### 5.2 Step 2: プレビューとライブラリ基盤

- スキャン直後:**保存・推論前にユーザー確認**（§2.2）。
- §9 に沿い、**Sandbox ディレクトリ構造・メタデータ**（SQLite またはオブジェクトボックス等はチーム規約で決定。MVP は単一 DB + ファイルパスで可）。
- サムネイル生成（一覧用）。

**完了条件**: スキャン → 確認 → ディスク保存 → ホームから再表示、が途切れない。

## 6. Phase C — Step 3〜4（推論とマスク）

### 6.1 Step 3: 推論パイプライン

- PoC コードを **サービス層**（例: `InpaintingRepository`）に移植。モデルは **assets 同梱**を最初に推奨（オフライン・デバッグ容易）。初回 DL は後から差し替え。
- **キャンセル**: `Isolate` または compute + キャンセルトークンで、UI スレッドをブロックしない（§2.2）。
- **進捗 UI**: 不定プログレスでも可。可能なら段階表示（前処理 / 推論 / 後処理）。

### 6.2 Step 4: マスクと消去強度

- **自動マスク**: HSV/LAB しきい値 + モルフォロジー、プリセット（鉛筆/赤/青の「候補」）。
- **手動マスク**（§8）: ブラシ・消しゴム・サイズ・ピンチ・Undo・オーバーレイ。`CustomPainter` + タッチ座標をマスクバッファに反映。
- **消去強度**: マスク膨張・ぼかし or ブレンド（ラベルと実装を一致）。

**完了条件**: Before/After 同一画面（§6）、低品質時も元画像保持で再編集（§2.2）。

## 10. アーキテクチャ指針（実装時）

- **レイヤ**: UI（ページ） / ユースケース（1 フロー 1 メソッド） / インフラ（ファイル、DB、ML、ONNX）に分離。テストが書きやすい単位。
- **状態管理**: MVP は `StatefulWidget` + 小規模 `ChangeNotifier` でも可。肥大化したら Riverpod / Bloc に移行する判断基準を「画面数 > 10」等で事前に決めてもよい。
- **モデル ONNX**: アプリ本体は **抽象 `InpaintingEngine`** に依存し、入出力だけ固定。モデル差し替え時に UI を触らない。
